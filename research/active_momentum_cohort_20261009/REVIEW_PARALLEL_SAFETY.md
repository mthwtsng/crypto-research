# Parallel collection review

Reviewed `collect_cohort.py` and `rpc_pool.py` on 2026-10-09. This is a collection-integrity review; no RPC calls, simulations, or edits to the collector were made. `collect_cohort` imported offline with `PYTHONDONTWRITEBYTECODE=1 python3`; `python` is not installed in this environment.

## Preserve these admission and provenance checks

- Count the target from distinct mints that finish full verification. A rejected or still-running candidate does not count toward 2,000. Continue through replacements when candidates fail, and report candidate-pool exhaustion as incomplete.
- Keep the deterministic day-interleaved candidate order. Give every candidate a sequence number and let one coordinator commit outcomes in that order, even when workers finish out of order. Otherwise process timing changes which 2,000 coins enter the cohort. De-duplicate by mint before dispatch and again when merging resumed results.
- Treat cached shortlist metrics as prefilters only. Recompute the final metrics from the complete source history. For cached census/shortlist files, validate their day/date, completion or exhausted-pagination marker, decoder/version, and unique mint keys before using them; the current loaders accept an existing file without those checks.
- Keep full-history canonical parity: every successful source curve group must match the approved integer adapter at each transaction, while token-account balances and transfers reconcile without invented inventory. Preserve failed receipts as no-ops and keep their fees/source evidence.
- Preserve the current thresholds and timing: 50 successful curve-trade transactions; at least 12 SOL peak or an authenticated migration; 25 distinct non-creator/deployer buyers with a buy of at least 0.05 SOL; creator plus configured-creator holdings at or below 10% of released supply at the first transaction reaching the peak; reject unknown positive token-account ownership. Continue to measure peak after whole transactions.
- Authenticate migration instructions and their curve/pool bindings. For admitted migrated coins, require exhausted pool history through exactly migration time + 3,600 seconds and verify the migration/open signature. The current collector now fetches this potentially large pool history after curve qualification; that is a safe RPC reduction because the migration itself is authenticated from the curve history first.
- Keep finalized block signature/index checks for every retained curve, repair, failed, and pool receipt. The per-mint code already de-duplicates slots; cross-mint reuse is safe only when the exact finalized block response is cached and each receipt's index is checked against it.

## Safe ways to reduce work

- Parallelize independent candidate verification, but keep a single coordinator responsible for mint claims, deterministic outcome commits, progress, manifest, rejection list, status, and completion record. Workers should return one per-mint result or failure and should not rewrite shared cohort-level JSON/Markdown files.
- Keep the worker queue bounded. Stop dispatching when the ordered coordinator has admitted 2,000. If already-dispatched work finishes afterward, record it separately as verified-but-unselected; do not append it to the cohort, count it twice, or claim it was never verified.
- Make per-mint claims process-safe (for example, an exclusive claim/lock released in `finally`). Multiple workers on the same mint can race on `raw_curves`, `raw_pools`, `bound_curve_tapes`, and `audits`; atomic rename prevents torn individual files but a last-writer-wins race can still pair artifacts from different runs.
- Use a process-safe lock for each exact RPC cache key around cache recheck, request, and atomic save. The current PID/thread-specific partial filenames plus `replace()` avoid the old fixed-temp-file collision, but separate processes can still issue the same uncached request and overwrite the same final key. Keep incomplete `.partial` files out of reads.
- Coordinate provider pacing and backoff across processes, not just threads in each process. The current in-memory `LOCK`/`NEXT` state is process-local; a 0.20-second schedule per process can multiply request rate when several worker processes run. Apply one shared provider schedule/cooldown, especially for Alchemy address-history and `getBlock` traffic, while preserving the existing fallback order and exact request parameters.
- Share finalized `getBlock` signature responses across candidates through the exact-key RPC cache; do not skip index validation or substitute transaction-list ordering. Use a per-key lock so parallel candidates sharing a slot do not refetch it concurrently.
- Cache/reuse account repair history only when the exact address and bounds match, and only accept a complete, exhausted response. Preserve the rule that each repaired receipt is merged, ordered, and the whole source is replayed from creation before admission.
- Keep all imports side-effect free: set `sys.dont_write_bytecode = True` before helper imports or run workers with `PYTHONDONTWRITEBYTECODE=1`. Use a guarded process entry point so imports do not start workers or collection.

## Concurrency hazards to close

- `verify()` currently trusts a cached audit when its version matches and the bound tape exists; it does not check the audit's `status`, mint, or required artifact contents. Validate those fields and the migration pool coverage before treating a cache hit as an admitted result. If verification semantics change, bump the verifier version or record a source/config fingerprint so older audits cannot bypass new checks.
- Shared `RPC_EVENTS.jsonl` writes need a process-safe append/lock or per-process telemetry files merged by the coordinator. Keep telemetry diagnostic; a partial telemetry line must not affect source acceptance.
- Write shared manifests and progress through one coordinator using atomic replacement. Do not let workers independently read-modify-write global lists: that can lose successful rows, duplicate rejections, or publish a target count inconsistent with the manifest.
- Use a process start method that does not inherit potentially held thread locks, or create workers before any RPC threads start. Each process has separate Python globals, so in-memory `DISABLED`, pacing, cache maps, and candidate `seen` sets are not cross-process coordination.

## Coordinator draft review

Read-only review of the current `parallel_collect.py` and `rpc_pool.py` draft:

- The five existing manifest rows are deduplicated through `selected_mints`; later `flush_ordered()` admissions also update that set. The coordinator uses explicit `spawn`, one coordinator owns manifest writes, RPC cache misses are locked across processes, and in-flight results stay in per-mint staging. It stops admitting at exactly 2,000 and waits for submitted workers before reporting staged verified extras. These parts preserve the hard cap.
- `flush_ordered()` has the required uniqueness update now. Still, `extra_audits` preselects every valid current-version audit absent from the old manifest before ordered flushing. Those successes can be at later queue positions than an unresolved earlier candidate, so they can count toward the target outside the queue prefix. Keep only the five prior manifest admissions as the explicit salvage exception; seed other validated audits as known outcomes and admit them when the ordered cursor reaches them. If all prior audit-only recoveries are to be preserved up front, disclose that ordering exception in the result provenance.
- `_write_complete_marker()` currently writes `staged_verified_extras: 0` unconditionally, while final `PARALLEL_STATUS.json` calculates the actual extras after workers drain. Derive the marker count from the same validated staged set or omit the field; otherwise the completion marker can disagree with status even though the 2,000 admitted count is correct.
- Failure handling is conservative: known threshold/parity failures can be rejected; provider, block-coverage, pool-coverage and unrecognized errors remain retryable, and the unresolved head prevents committing later candidates. Keep `migration_curve_binding_missing` retryable as well: a missing migration binding is unresolved evidence, not proof that a migration did not occur.
- Resume validation replays cached curve parity and checks the one-hour pool window. For full migration authenticity, `validated_cached_audit()` should also re-decode the raw curve receipts and require exactly one migration whose signature, mint, pool and bonding curve match the cached migration record. The current validator confirms only that the cached migration signature appears somewhere in the cached pool receipts.
- The queue builder validates the census day and exhausted pagination but does not require the census decoder version. Check the expected `bound_curve_v1` (and a present day field) before freezing the queue so an older census artifact cannot silently change the migration candidate set.
- Promotion archives existing regular files before replacement and callers validate staged audits first. The moves across raw, pool, bound tape and audit are still a multi-file operation; a crash can leave canonical artifacts temporarily mixed. Keep the preserved prior copies and rely on independent resume validation before admission, as the draft does.
