# Read-only review of `accounting.py`

This is an implementation and receipt-reconciliation review, not a wallet PnL estimate or a copy-trading result. I read `accounting.py` without changing it and inspected one zero-inventory-to-zero-inventory cycle from each of the full `recent_*.json.gz` transaction-detail captures for 72MU, 4yFA, and 8dtx. Each capture contains 250 rows with `transaction`, `meta`, `transactionIndex`, and `full_rows_verified: true`. The slices cover only 72MU 2026-10-12 01:31–04:11 UTC, 4yFA 01:37–04:11 UTC, and 8dtx 2026-10-11 18:54–2026-10-12 04:11 UTC. The broader 21-day histories are not equal in coverage: 4yFA and 8dtx are capped at 10,000 rows. All findings below are limited to these receipts and code paths.

The cash figures above are sums of the owner’s native SOL and WSOL balance changes on the matched trade receipts. All six receipts have zero owner WSOL delta, so they verify the native component but do not exercise the WSOL component of `cash = native + ΔWSOL`. I am reporting the arithmetic as a receipt check, not calling these values profit.

Fees and extra SOL movements are present in the owner’s actual balance delta. For example, the 72MU entry debits a 90,000-lamport network fee, 0.001 SOL top-level transfer, two new-account rents totaling 0.00300228 SOL, and Pump CPI transfers in addition to the event quote; its sell also pays a 90,000-lamport fee and a 0.001 SOL top-level transfer. The 8dtx entry and exit each include a 0.00103 SOL top-level transfer, and their network fees are 0.00091085 and 0.000996716 SOL. These transfers look execution-related, but this review did not independently identify the recipients as validators or tips. Because the code sums account deltas, it includes them without needing a tip classifier.

The 4yFA buy receipt is a useful check against treating event quote fields as wallet cash: the Pump event reports `sol_amount` 2.926383171 SOL, while the owner’s native debit is 3.025007242 SOL. The receipt includes a 0.060005 SOL fee, 0.00203928 SOL account rent, and a 2.962962962 SOL Pump CPI transfer. The two sells each also have outbound System transfers and network fees. Using native balance deltas for cycle cash is the right basis for these transactions; `event_sol_raw` is an event diagnostic and is not the complete cash debit/credit.

## Findings for the accounting implementation

1. **Matched trade custody is internally consistent in these samples.** `tokens()` sums all pre/post token balances attributed to the owner, and the Pump event token deltas exactly match each selected receipt’s aggregate mint-balance change. Receipts are successful; no decode errors or tainted cycles occurred in the three selections. Fee-payer identification agrees with account key 0 in the inspected legacy and version-0 receipts. The zero-to-zero opening/closing rule is conservative and behaved as intended here.

2. **Cycle cash includes locked rent as an outflow, so it is not realized PnL by itself.** On 72MU, the buy creates the target token account and the WSOL account. The sell closes/refunds the WSOL account’s 0.00148844 SOL rent, but leaves the zero-balance target-token account open with 0.00151384 SOL rent. On 8dtx, the zero-balance target-token account also remains open with 0.00151384 SOL rent after the sell. In both cases the cash delta counts that still-recoverable rent as a cycle cash cost; a later close/refund would be classified outside the cycle. The 4yFA sample shows the other case: its target account is closed on the final sell and the 0.00203928 SOL rent is returned. Any economic-PnL use should separately mark retained account rent and pair subsequent refunds, while the current cashflow measure can remain an actual balance delta.

3. **Standalone transfers are not mistaken for cycle proceeds, but same-transaction cash is not decomposed.** If there is no owner token-balance change, the code sends cash to `nontrade` rather than a cycle. As a concrete inherited-inventory example, 72MU signature `62X5BQyt…31Q3TLyM` has a positive native cash receipt of 0.884087430 SOL while the owner sells 25,679,796,144,801 pre-existing token units to zero; it is excluded as `inherited_or_no_zero_inventory_opening`, not counted as a new cycle. However, any unrelated SOL deposit or withdrawal co-occurring in a transaction that also passes the single-mint trade match is included in that cycle’s balance delta. The three selected trade cycles contain outbound transfers, plausibly execution tips, and no unrelated inbound transfer; the code does not verify that interpretation. A same-transaction cashflow classifier or a clear account-cash-only label is needed before interpreting the measure as strategy PnL.

4. **Decode exceptions can bypass custody tainting.** In `analyze()`, the `except` around `D.events(t)` / `ammevents(t)` appends to `decode_errors` and immediately continues. It has already computed token `changes`, but does not add those changes to `excluded` or mark an active mint cycle tainted. If decoding throws on a receipt that changes an owner’s token inventory, a later valid exit could still be counted as a clean completed cycle with the intervening movement omitted. None of the inspected receipts triggered this branch. On decode failure, changed mints should be recorded and any active cycle tainted; an opening inventory-changing receipt should remain excluded.

5. **The multi-account taint rule may discard valid aggregated custody cycles.** `observed_accounts[mint]` is a set of every owner token-account address seen for a mint, and any active cycle is tainted once this set exceeds one. But `tokens()` already aggregates all balances for that owner and mint, and the event-delta equality check uses that aggregate. Multiple owned accounts alone do not imply missing custody; this can be conservative over-exclusion when balances are fully observed and reconcile. No selected sample was tainted, so the effect was not measured here.

6. **Open cycles are excluded from completed-cycle cash, as they should be, but require a visible separate inventory card.** `active` positions are returned in `open_observed_cycles` with retained raw token amounts and no mark; `cycles` contains only completed, untainted cycles. None of these three 250-row slices ended with an open cycle. The caller must not present completed-cycle cash as whole-wallet performance or treat open inventory as zero. The analysis result itself does not include a mark venue/time or reconcile locked rent and open inventory to a full end balance.

7. **Coverage status is not carried into the accounting result.** `source_rows()` loads every page it finds, but it does not return or enforce `collection.json` history status, common interval, or page-cap metadata. Current 4yFA and 8dtx history captures are capped at 10,000 full rows, whereas 72MU has 4,014 rows and a complete history status. The returned min/max timestamps help expose spans, but summaries can still be mistaken for comparable full-window results without the manifest’s truncation status. Preserve that status and coverage window alongside every wallet result.

8. **PumpSwap was not empirically exercised by this sample.** The selected 250-row slices produced no PumpSwap IDL events; all three selected cycles are Pump curve trades. The PumpSwap path in `ammevents()` appears structurally coherent for this collector’s `jsonParsed` records: it filters authenticated successful `A.events(t)` logs and joins the event pool to a decoded instruction’s pool/base/quote-mint accounts, then requires owner-mint deltas and a WSOL quote. The inspected version-0 record shape also has resolved key arrays aligned with balance indices. Still, there is no PumpSwap cycle here against which to verify event-to-pool attribution, user matching, quote amount, or cross-venue custody. Label PumpSwap accounting unverified until a complete raw PumpSwap cycle is traced receipt by receipt.

No replay, backtest, or source modification was made.
