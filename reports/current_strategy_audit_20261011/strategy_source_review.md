## Shared implementation and measurement issues

**Atomic receipt versus signal grouping.** The runner decodes each successful Pump event, applies every event in a receipt, and then retains only the last event for each mint before evaluating a signal ([curve_detector.rs:17](../../src/bot/pump_receipt_decoder.rs#L17), [curve_detector.rs:85](../../src/bin/curve_detector.rs#L85), [curve_detector.rs:2243](../../src/bin/curve_detector.rs#L2243)). Waiting until the receipt is complete is consistent with atomic execution. But strategy accumulators mutate once per event, not once per signature: S3 may count one transaction as two buyer groups; conversely, S1/S4 current-event checks see only the last event for a mint and can miss a qualifying earlier buy inside that same transaction. Detect S3’s two distinct signatures and aggregate signal evidence at transaction scope before changing thresholds.

**Clock and placement.** `observation_trades` sets the strategy timestamp from `received_at_ms`, and the bot queues a default 70ms delay from processing time; the configurable delay has a 30ms floor ([curve_detector.rs:85](../../src/bin/curve_detector.rs#L85), [1748](../../src/bin/curve_detector.rs#L1748)). The latest snapshot reports 70ms, but that is a receive-clock quote assumption, not measured source landing-to-fill latency. The accuracy contract requires the central p=0.80 and p=0.85 placement mixtures, anchored reactive exits, and fast/slow brackets. The current logs do not supply these, and actual curve or AMM fills are absent. The 50ms timer loop evaluates while feed continuity is fresh; it suspends curve updates after a stream gap over two seconds ([curve_detector.rs:1306](../../src/bin/curve_detector.rs#L1306)). Keep receive time, chain block time, transaction index, and hypothetical landing time separate in any comparison.

**Paper quote state is not a complete counterfactual path.** A paper buy or sell applies its own reserve change, but the next decoded external receipt replaces the curve reserves with the authenticated public reserves ([curve_detector.rs:349](../../src/bot/curve_detector.rs#L349), [curve_detector.rs:463](../../src/bot/curve_detector.rs#L463)). This makes shadow quotes useful operational observations but not a replay in which every later external trade executes against the changed reserves caused by the paper order. The net direction of that difference is not a constant haircut. For migrated positions, the source explicitly describes snapshots as diagnostic rather than a reconstruction of each external AMM transaction ([curve_detector.rs:1404](../../src/bot/curve_detector.rs#L1404)).

**Ticket, reserve ratio, fees and rent.** The source uses a fixed 0.50 SOL gross ticket, a 0.001505 SOL standard fee per successful buy/sell, and a 0.000505 SOL failed-buy guard fee; the buy guard retains 90% of the signal-time token quote ([curve_detector.rs:43](../../src/bot/curve_detector.rs#L43), [curve_detector.rs:1111](../../src/bot/curve_detector.rs#L1111), [curve_detector.rs:1256](../../src/bot/curve_detector.rs#L1256), [curve_detector.rs:634](../../src/bin/curve_detector.rs#L634)). Protocol/creator fees come from each supported receipt quote. No rent reserve, token-account rent debit, or rent refund appears in the paper position/accounting fields, so rent behavior is unknown and omitted.

For S1, a 0.50 SOL ticket is 50% of a 1 SOL **pre-buy real-SOL reserve** and 10% of a 5 SOL pre-buy reserve. The logged `buy_impact_pct` is `(post real reserve / pre real reserve − 1) × 100`; its denominator is the pre-buy real reserve. Thus an approximately 11% value is real-reserve growth (near 0.50/4.5), not an 11% spot-price move or measured net round-trip loss. A finite-size, fee-inclusive sell-back quote is needed to measure immediate round-trip friction; this audit did not calculate one. The current fixed ticket should be compared with the user-authorized 0.50–1.00 SOL research sizing range without assuming linear scaling.

**Breaker restore.** The source initializes five per-family breakers with registry-matching streak/window/cooldown values, but checkpoint restore replaces the full map with whatever keys were saved ([curve_detector.rs:2168](../../src/bot/curve_detector.rs#L2168), [curve_detector.rs:536](../../src/bin/curve_detector.rs#L536)). Admission treats a missing breaker as “not cooling,” so a partial map bypasses that family’s cooldown ([curve_detector.rs:441](../../src/bin/curve_detector.rs#L441)). The frozen 23:12 summary and runtime both contain only S4 while reporting breakers enabled. The source also has no registry global rolling 24h −2 SOL / 12h pause and no 0.25 SOL cooldown-probe recovery. This is a control/admission defect, separate from entry alpha.

**Epoch and capacity provenance.** The code defaults to `MAX_POSITIONS=10` and a 0.50 SOL ticket; the research authorization is a 15 SOL cash-funded comparison with no research position cap, while live capacity remains two. Summary telemetry omits the effective position cap, entry mode and build/config hash; runtime VM IDs can persist across checkpoint restore. The newest variant rows show `live_entry_mode=reclaim`, but the frozen file set cannot establish the deployed binary or all environment values. Do not use source defaults as proof of the host’s live or shadow settings.
